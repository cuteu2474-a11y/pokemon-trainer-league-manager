위 기능을 처음부터 다시 만드는 대신, 다음 연결과 검증을 진행합니다.

## 1. 먼저 수정할 연결 문제

### 1-1. 자율 훈련을 개별 CA/PA에 연결

- [ ] 자율 훈련의 성장 대상 선정과 성장 처리를 `statCA/statPA` 기준으로 교체합니다.
- [ ] 주간 활동·AI 구단 훈련의 이전 `power < 99`, `power < 94` 제한을 개별 PA 상한으로 정리합니다.
- [ ] 육성 방향이 실제로 성장할 능력치 선택에 반영되게 합니다.
- [ ] 훈련 보고서도 “공격 CA 70→71”처럼 실제 변경한 값을 보여줍니다.

**현재 확인:** [자율 훈련](../assets/matchday.js)의 `trainMon/trainTrainer`는 종합 CA·PA·GP를 읽습니다. [능력치 이전](../assets/ability-ui.js)은 포켓몬의 기존 `ca/pa/gp`를 삭제합니다. 이 상태에서는 해당 자율 훈련이 성장 대상을 찾지 못할 수 있습니다. 일부 구형 주간 훈련은 평균 `power` 증가를 개별 CA 증가로 바꾸는 호환 처리가 있지만, 자율 훈련까지 통합된 구조는 아닙니다.

**완료 기준:** 새 게임과 이전 저장 모두에서 주간 진행으로 실제 CA가 증가하고, 각 PA를 넘지 않으며 PA 자체는 변하지 않습니다. 한 주를 다시 열어도 성장 보상을 중복 지급하지 않습니다.

### 1-2. 모든 선수단 생성 경로의 기술 적합성 통일

- [ ] 별도 리그 엔진의 초기 선수단도 해당 종이 배울 수 있는 기술로 생성합니다.
- [ ] 경기 API에서 기술 존재 여부뿐 아니라 종별 습득 가능 여부, 특성·도구의 리그 사용 규칙을 검증합니다.
- [ ] 구버전의 잘못된 세트는 보유 기록을 보존하면서 이전하거나, 수정이 필요한 이유를 표시합니다.
- [ ] 레벨이 없는 게임에 맞춰 기술 습득 기준을 문서화합니다.

**현재 확인:** 웹 자동 편성·기술 연구는 learnset을 사용하지만, [별도 리그 선수단 생성](../src/league/pokemon-rosters.js)의 `movesFor`는 공통 공격 목록에서 고릅니다. [경기 API 변환](../src/web/match-service.js)은 기술이 엔진에 존재하는지는 검사하지만 종별 습득 가능 여부는 검사하지 않습니다.

**완료 기준:** 새 선수단·야생 포켓몬·기술 연구·이전 저장이 같은 기술 등록 규칙을 따릅니다. 사용할 수 없는 세트는 경기 시작 전에 확인됩니다.

### 1-3. 포켓몬 소유자와 개체 ID 검증

- [ ] 포켓몬마다 고유 개체 ID와 포획 트레이너 ID를 저장합니다.
- [ ] 편성·경기 등록에서 다른 트레이너의 포켓몬을 사용할 수 없도록 검증합니다.
- [ ] 이적·계약 종료·후보 승격에도 원래 개체와 소유자 ID를 보존합니다.
- [ ] 이미 보유한 포켓몬에는 현재 소속을 기준으로 ID를 한 번만 부여합니다.

**현재 확인:** 탐색 후보는 해당 트레이너 안에서 관리하고 이적은 트레이너 객체를 이동하지만, [후보 생성](../assets/pokemon-expedition.js)과 [경기 등록](../src/web/match-service.js)에 명시적인 포획자 ID 확인이 없습니다. 화면에서 다른 사람에게 옮길 버튼이 없는 것과 데이터 검증은 별개입니다.

**완료 기준:** 이름이 같아도 개체를 구분하며, 다른 트레이너 소유 개체의 등록은 거절합니다. 이적 후 복제·유실이 없습니다.

### 1-4. 레벨 제거 후 남은 특수 기술 처리

- [ ] 일격기 명중·사용 조건과 셸사이드암 등 레벨을 참조하는 특수 콜백을 전수 확인합니다.
- [ ] 남은 참조마다 리그 전용 규칙을 정하고 실제 전투·AI 가상 전투에 함께 적용합니다.
- [ ] 변신·폼 변경·혼란·고정 피해가 같은 능력치 체계를 따르는지 검증합니다.

**현재 확인:** 일반 피해·혼란·나이트헤드·지구던지기·사이코웨이브는 이미 [전용 피해 처리](../src/battle/level-free-damage.js)에 연결됐습니다. 남은 희귀 예외는 [레벨 제거 문서](level-free-ca-pa.md)에 기재돼 있습니다.

**완료 기준:** 레거시 레벨 값만 바꿔도 경기 결과가 달라지지 않고, 실제 전투와 AI 예측이 동일한 규칙을 사용합니다.

## 2. 리그와 운영을 완성할 작업

### 2-1. 다른 구단의 경기에도 실제 전투 엔진 적용

- [ ] 웹의 다른 구단끼리 19경기를 Showdown 연승전으로 연결합니다.
- [ ] 계산 진행률·실패 재시도·완료 경기 재사용을 마련합니다.
- [ ] 모든 경기가 완료된 뒤 주차와 순위를 한 번만 반영합니다.
- [ ] 웹과 별도 리그 엔진의 일정·점수·동률·승강 규칙을 통일합니다.

**현재 확인:** [웹 경기 연결](../assets/matchday.js)은 우리 경기 결과를 주입하고 나머지는 기존 간이 계산을 사용합니다. [리그 엔진](../src/league/season.js)에는 실제 경기 어댑터가 있지만, [실제 리그 통합 테스트](../tests/real-league-integration.test.js)도 한 경기만 실제 전투를 사용합니다. [360경기 테스트](../tests/league-season.test.js)는 일정과 집계 검사용 결과를 주입합니다.

**완료 기준:** 360경기를 모두 실제 엔진으로 완료하고, 구단마다 18경기·승점·득실이 맞습니다. 중단 후 재개해도 결과가 중복되지 않고 다음 시즌 승강까지 이어집니다.

### 2-2. 개인 컨디션·파견·경기 일정 연결

- [ ] 트레이너와 포켓몬의 개별 피로·회복 상태를 관리합니다.
- [ ] 경기 준비 화면에서 실제 컨디션과 파견 상태를 보여줍니다.
- [ ] 파견 중 훈련·경기 출전의 허용 범위를 정하고 일정 충돌을 처리합니다.
- [ ] 다음 공식 경기의 회복과 같은 단체전 안의 HP 10% 회복을 구분합니다.

**현재 확인:** 경기 준비는 개인 컨디션을 미측정으로 표시합니다. 탐색은 다음 주 결과를 받지만 개인 컨디션과 경기 등록에 통합돼 있지 않습니다.

**완료 기준:** 활동·회복·파견 상태가 저장 후에도 유지되고, 준비 화면의 상태와 실제 출전 가능 여부가 일치합니다.

### 2-3. 탐색·포획·개체 감별의 역할 정리

- [ ] 탐색·포획 능력과 개체 감별 능력의 역할을 확정된 기획과 맞춥니다.
- [ ] 종 다양성·희귀종 조우와 같은 종 내 개별 CA/PA 분포를 각각 검증합니다.
- [ ] 표시 확률과 실제 추첨이 같은 함수를 사용하도록 현재 구조를 유지합니다.
- [ ] AI 구단도 장기 전력 확보를 위해 탐색을 사용하도록 연결합니다.

**현재 확인:** [현재 탐색](../assets/pokemon-expedition.js)은 `skill/captureSkill`을 따로 사용하고, 후보 CA/PA에도 탐색 skill이 들어갑니다. 별도 개체 감별 수치는 없으며 종별 조우 가중치는 탐색 목적·시간대가 결정합니다. [기획](TRAINER_SYSTEM.md)의 능력치 역할과 차이를 정리해야 합니다.

**완료 기준:** 다른 조건을 고정했을 때 각 능력이 의도한 확률에만 영향을 주고, 포획 완료 개체의 CA/PA를 사후 변경하지 않습니다.

### 2-4. 보유 포켓몬과 출전 6마리 분리

- [ ] 트레이너가 포획한 전체 포켓몬을 보관할 명단을 만듭니다.
- [ ] 그중 출전 6마리를 선택하고 변경 내역을 저장합니다.
- [ ] 후보 영입 때 기존 포켓몬을 반드시 방출해야 하는 현재 흐름을 개선합니다.
- [ ] 이적 시 출전 중인 6마리뿐 아니라 보유 포켓몬 전체가 동행하게 합니다.

**현재 확인:** [탐색 등록](../assets/pokemon-expedition.js)의 `recruit`는 기존 6마리 중 하나를 방출하고 교체합니다. [기획](TRAINER_SYSTEM.md)은 6마리를 초과하여 보유하되 경기에는 6마리를 선택하는 구조입니다.

**완료 기준:** 보관·출전·방출을 구분하고, 출전하지 않는 개체도 소유권·육성 기록을 유지합니다.

### 2-5. 진화·특성·도구를 운영 화면에 연결

- [ ] 레벨 없이 진화할 조건과 비용을 정합니다.
- [ ] 개별 CA/PA·개체 ID·포획자·육성 기록을 유지하며 종과 전투 데이터를 갱신합니다.
- [ ] 단장과 트레이너의 역할에 맞춰 기술·특성·도구를 확인·조정할 흐름을 정리합니다.
- [ ] 특성·도구가 만드는 무효·피해 변화는 기본 타입 상성과 구분하여 표시합니다.

**현재 확인:** 엔진은 등록된 기술·특성·도구를 사용하고 전투 중 폼 변경을 처리합니다. 일반적인 진화 운영과 장비 관리까지 완성된 것은 아닙니다. 기술 표의 배율도 최종 피해 예측이 아닌 기본 타입 상성입니다.

**완료 기준:** 화면에 표시한 세트와 실제 경기 세트가 일치하고, 진화·세트 변경 후에도 저장과 관전이 정상 동작합니다.

### 2-6. 은퇴·계약·재정의 장기 운영 점검

- [ ] 포켓몬 8시즌 일괄 은퇴와 즉시 신예 대체를 장기 육성 구조에 맞게 조정합니다.
- [ ] 트레이너 은퇴 때 포켓몬 동반 은퇴를 유지할지 확정하고 기획에 반영합니다.
- [ ] 계약 만료·은퇴·승강·이적 이후에도 출전 5명과 각 6마리를 확보할 수 있게 합니다.
- [ ] 수입·연봉·훈련·탐색·이적 지출을 다중 시즌으로 확인합니다.
- [ ] 시즌 수만으로 구단 전력과 자산이 무한히 상승하지 않는지 확인합니다.

**현재 확인:** 은퇴·아카데미·이적은 이미 있습니다. 다만 `index.html`은 포켓몬을 활동 8시즌에 자동 대체하고, 트레이너 은퇴 때 담당 포켓몬도 함께 은퇴시킵니다. 구형 생성 경로와 [개별 CA/PA 이전](../assets/ability-ui.js) 사이의 연결도 점검해야 합니다.

**완료 기준:** 최소 10시즌 운영에서 선수단 공석·음수 재정 처리 누락·계약 중복·개체 복제가 없고 세대교체가 가능합니다.

## 3. 마무리할 안정성·검증 작업

- [ ] 기존 저장·새 저장에 명시적인 버전을 두고 이전을 한 번만 적용합니다.
- [ ] 저장 실패를 화면에서 알리고 내보내기·가져오기·복구를 마련합니다.
- [ ] 경기 기록 누적으로 브라우저 저장 한도를 넘는 상황을 처리합니다. 현재 `persist`는 실패 시 콘솔 경고만 남깁니다.
- [ ] 새 게임 → 훈련·탐색 → 경기 준비 → 실제 경기 → 저장·복원 → 이적·은퇴 → 승강·새 시즌 흐름을 브라우저에서 검증합니다.
- [ ] iPad 가로·세로 화면에서 편성·탐색 확률표·기술 패널·보고서의 잘림과 터치 조작을 확인합니다.
- [ ] AI가 미공개 상대 기술·도구·특성 및 엔진 난수 상태를 예측에 사용하는 범위를 점검합니다. 현재 [가상 전투](../src/battle/showdown-rollout.js)는 실제 전투 상태를 복제하므로 정보 제한 검증이 필요합니다.
- [ ] 주요 상성·장기전·회복·교체·폼 변경·PP 고갈을 포함한 재현 가능한 AI 비교 경기를 구성합니다.
- [ ] [기획서](GAME_DESIGN.md)와 [연결 현황](ui-integration-status.md)의 오래된 “기획 단계”, 레벨·GP 중심 설명, 과거 테스트 개수를 최신 구조와 맞춥니다.

## 별도로 규칙을 확정할 항목

- 단일 타입 전문 편성 보너스의 수치·적용 대상·중복 규칙. 현재 전투 주입 코드에는 적용이 확인되지 않습니다.
- 레벨 없는 진화 조건과 희귀 특수 기술의 리그 규칙.
- 파견 중 공식 경기 출전 여부, 포켓몬 보유 상한.
- 트레이너 은퇴 시 전속 포켓몬 처리와 포켓몬 은퇴 시점.
- 개별 CA/PA 산식과 초기 분포의 최종 밸런스.

확정되지 않은 수치를 먼저 고정하지 않고, 이미 합의된 방향 안에서 구현 가능한 연결 문제부터 진행합니다.
